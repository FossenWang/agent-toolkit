# agents-draft

## 背景

- `AGENTS.md` 这类指令文件会被自动加载进会话。会话中途改动，下一轮就按新内容执行，前半段和后半段可能遵循不同规则。
- 指令文件影响面大，零散小改不容易看清整体变化。
- 原设计是强制流程：只要改这类文件就必须走草稿、审阅、合入。实际使用中门槛过高，改为由模型或用户按需触发。

## 设计抉择

**只管理已加载的指令文件。** 判据是「这次改动会不会改变当前会话的上下文」。没被加载的文件改了不影响任何会话，管理它们只是增加摩擦。

**用自省而不是扫描仓库。** 上下文里已经标明哪些指令来源被加载，直接读比复刻各 harness 的发现规则可靠。不同 harness 暴露路径的能力不同，拿不到时问用户，不按约定文件名猜——猜错会改到根本没加载的文件。

**对话中 agent 自己读到的指令文件默认不管。** 那是会话内容，不是 harness 注入的指令，和在上下文中生效的规则不是一回事。

**不处理 skill。** skill 按需加载，不是常驻指令，改动成本和影响范围都不同。

**先起草再写回，且一次写完。** 草稿可以反复改、逐份审；审阅时把每份 diff 完整报告给用户，而不是只说「有改动」；diff 过长或草稿过大时用文件路径引用，不粘贴全文。一次性写回让整体变化更清楚，也减少会话中途规则抖动。

**草稿箱用标记文件定位。** 根目录放 `DRAFT.md`，它同时是说明和标记，不引入任何外部状态文件。只复用项目内的草稿箱；临时目录里的是一次性工作区，不写标记、下次重建。标记文件名用 `DRAFT.md`，避免和宿主目录里已有的 `README.md` 冲突。

**递归查找要排除干扰目录。** `.git`、`node_modules`、构建产物、缓存和 `.venv` 这类目录里可能藏着同名文件，也会拖慢查找。

**不把缓存当成主要理由。** 原设计认为每次改动都会让 prefix cache 失效。实际并非如此：部分 harness 对全局和向上发现的指令采用增量更新，当前会话已缓存的前缀仍然可用，缓存主要影响新会话。真正成立的理由是会话语义一致性。

**对模型可见。** 不设 `disable-model-invocation`，让模型按描述判断哪些文件该走草稿箱。这本身是一次试验：观察模型能否区分「已加载的指令文件」和普通文件。

## 未决

- 模型自主判断的准确率还没有数据。误触发或漏触发时，先调描述里的判据，再考虑加回显式调用限制。
