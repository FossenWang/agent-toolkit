# agents-draft

改指令文件时先放进草稿箱。草稿是唯一的工作副本，确认后才写回本体。

正在生效的指令文件（AGENTS.md 等）一改，当前会话下一轮就会按新内容执行，容易前后不一致；所以不在原地改，攒成一次写入。

## 流程

1. **收集目标**

   - 自省：从当前会话上下文里识别已经加载的指令文件，只处理能拿到路径的，不扫描仓库猜。
   - 非 harness 加载到上下文中的指令文件，比如会话中 agent 自己读到的指令文件，默认不管理。
   - 起草前再扫一遍，嵌套或按需加载的指令可能在会话中途才出现。
   - 用户指定要放进草稿箱的文件。
   - 列成清单和用户确认。

2. **定位草稿箱**

   - 用户本次指定：直接用，没有 `DRAFT.md` 就写一份。
   - 否则在项目根以下递归查找名为 `DRAFT.md` 的文件，找到就复用；出现多个时取路径最短的，并在报告里说明。查找时排除版本库元数据、依赖和缓存目录，例如 `.git`、`node_modules`、`dist`、`.cache`、`.venv`。
   - 项目内也没有：在系统临时目录下新建一个名字形如 `draft.XXXXXX` 的目录，一次性使用。
   - 草稿箱根目录放一份 `DRAFT.md`，既是说明也是标记。
   - 只复用项目内的草稿箱；临时目录里的不写 `DRAFT.md`、不记录，下次不扫描。
   - 项目根取仓库顶层目录；不在仓库里就用当前目录。

3. **起草**

   - 在草稿箱里镜像本体路径，扩展名前加 `.draft`。
   - `AGENTS.md` 对应 `<草稿箱>/AGENTS.draft.md`。
   - 仓库外的绝对路径放到 `<草稿箱>/_external/<去掉开头斜杠的路径>`。
   - 草稿可以反复迭代。

4. **审阅**

   - 把每份草稿和本体做 diff，结果明确报告给用户。
   - 逐文件展示 diff 内容；新建的文件没有本体可比，就把草稿完整给出。
   - diff 过长或新建草稿过大时，不要粘贴全文，直接给出文件路径。
   - 不要只说「有几处改动」，也不要省略具体内容。
   - 等用户确认后再写回；用户要求调整就回到起草。

5. **写回**

   - 确认后把草稿一次性写回本体，不逐个文件问。
   - 写之前确认本体没有在会话期间被外部改动。

6. **清理**

   - 删掉已写入的草稿。
   - 项目内的草稿箱只留 `DRAFT.md`。
   - 临时草稿箱如果本次创建且已全部写回，整个目录删掉。
